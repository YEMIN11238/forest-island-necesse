# Mosslume 视觉重做 PRD 0.3

更新日期：2026-10-22。产品名称沿用 Mosslume（苔光之岛）。当前运行基线为 0.2.0；0.3 是本次目标版本，尚未实现或验收。本文取代此前零散的视觉修改要求，现有玩法与已生成素材继续作为基础。

## 1 本次决定

把现有小岛重做成参考视频中清晰、密集、明亮且有层次的像素场景。重点重做显示、植物运动、动态光影、水面和场景编排。保留现有采集、制作、建造、种植、居民、库存及保存系统，不再更换玩法底座。

首个交付是可操作的代表性场景，包含树木、灌木、篝火、箱子、工作台、小屋与曲折岸线；通过画面和性能对照后再覆盖整张岛屿。最终交付仍是 Mac 游戏应用，浏览器素材预览不作为游戏完成证明。

本期的价值是让玩家愿意停留、观察和操作这座岛。当前评价来自发起人的实际使用反馈，不将个人偏好写成已验证的市场需求，也不加入收入、留存或工期承诺。

## 4 画面规范

### 4.1 像素与相机

定义一套世界像素尺度，导出的原生尺寸、脚点、碰撞格和显示倍率同时登记。先检查已有素材，避免靠任意小数缩放逐件凑大小。输出端允许采用专门的像素缩放着色器，但不能叠加多个过滤器补救前面已经模糊的贴图。

主验收使用固定常用窗口尺寸，另检查 Retina、窗口缩放及全屏。记录逻辑分辨率、帧缓冲尺寸和显示倍率，区分世界与 UI 缩放。镜头移动和树冠形变需要兼顾连续运动与像素清晰，不能用所有坐标强制取整替代设计。

### 4.2 比例与构图

先从 E01 标定角色、成熟树、小屋、灌木、道路宽度的相对比例，形成带标注的目标构图，作为后续固定依据。参考画面分辨率和遮挡有限时记录区间及取样对象，不填造精确测量。

一棵树不应占据近似房屋的视觉体量；小植物不能被随意放大成另一类树。高密度主要布置于林缘与背景，营地、入口、工作区域和主要行走路线保持可读。植物多样性来自轮廓、叶色、层次与组合，不能只堆同一种贴图。

道路需要弯角、过渡、分叉、端头及散落边缘。土地和海洋之间包含草边、土侧面、浅水过渡及投影，不能只有一圈统一黑边。布局调整需同步检查碰撞与交互距离。

### 4.3 颜色与光照

环境层保留青蓝与绿色的色彩信息，局部光以篝火和灯具的暖色建立焦点。光源近处更亮，远处渐弱；树后和物体背光面仍有形体。发光物的柔光可以柔和，精灵本身的像素边缘不随之模糊。

用关闭局部光、单篝火、多光源、不同环境光四种状态检查同一场景。白天与夜晚可以辨认；本期先把参考夜景做好，再保证时间变化不会破坏既有层次。

## 6 开源方案与接入约束

以下为 2026-10-22 已核验的候选源码。选择依据是功能、许可与当前底座的适配程度，不按仓库热度保证效果。各项目尚未通过本机 0.3 场景验收。

| 模块 | 首选参考 | 接入方式与边界 |
| --- | --- | --- |
| 最终像素显示 | [Sharp Shimmerless Shader](https://github.com/Woohyun-Kang/Sharp-Shimmerless-Shader)，CC0 | 比较并替换当前最终缩放着色器；先修精灵采样。其输出 Alpha 固定为 1，适合整屏合成结果，不能原样套透明树贴图 |
| 植物风动 | [Simple Wind Shader 2D](https://github.com/JaccomoLorenz/godot-simple-wind-shader-2d)，MIT | 移植连续时间、顶点形变与根部权重，用少量网格表达树冠弯曲；Godot 脚本不能直接安装进 Java |
| 完整光影流程 | [SDV Radiance](https://github.com/PHUICMT/SDV-Radiance)，MIT | 优先参考精灵轮廓、方向光与局部灯光阴影、水面相关流程；从 SMAPI／MonoGame／HLSL 适配为当前 OpenGL 管线，先证明单树与岸边可用 |
| 备选精灵光影 | [Pixi Lights and Shadows](https://github.com/dobrado76/pixi-lights-and-shadows)，MIT | 当 Radiance 的渲染依赖难以收敛时，比较其 GLSL、遮挡与接收层分离方案；不与另一套完整光影流程长期叠加 |
| 俯视水面 | [GDQuest Godot Shaders 1.0.0](https://github.com/gdquest-demos/godot-shaders/releases/tag/1.0.0) | 复用 MIT 着色器中的纹理流动与颜色混合，贴图继续使用本项目素材；其演示贴图和模型另有 CC BY NC SA 许可，不混入素材包 |
| 相机平滑参考 | [Smooth Pixel Camera Demo](https://github.com/voithos/godot-smooth-pixel-camera-demo)，MIT | 需要时移植整数相机与最终小数补偿的方法；它不替代树冠自身的连续形变 |

接入时记录实际采用版本、源文件、许可证、改动和对应需求，保留第三方声明。未实际移植的项目只标记为参考；不能再把“研究过 SDV-Radiance”写成“已经完整接入”。

渲染实现应形成一条可追踪的流程：世界颜色与深度顺序 → 遮挡对象及高度 → 方向光和局部灯光阴影 → 受光与水面合成 → 适量发光 → 最终像素输出 → UI。具体通道与顺序由小场景验证确定，避免引入互相冲突的多个完整渲染框架。

阴影更新不再依赖逐帧重新生成全屏 CPU 像素数组作为常规路径。静态遮挡可缓存，光源或树冠变化时更新必要数据。先记录 CPU 与 GPU 帧时间和上传开销，再决定优化，不预先宣称已找到全部性能瓶颈。

## 8 验收方法与通过条件

### 8.1 固定对照条件

使用独立测试存档，固定镜头、岛屿状态、时间、天气与光源；保留 0.2 与 0.3 同条件截图及录像。记录机器、系统、窗口逻辑尺寸、帧缓冲尺寸、显示倍率、构建标识及素材版本。参考画面按同等场景比例对齐，不能把一张缩小截图与另一张全屏图直接判断清晰度。

静态清晰度用原尺寸与最近邻放大检查；运动用覆盖多个完整周期的原生帧或录像检查；性能用帧时间记录。录像本身卡顿时须核对应用记录，不能直接归因于游戏。

| 编号 | 对应需求 | 通过条件与证据 |
