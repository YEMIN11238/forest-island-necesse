# Mosslume 世界与 AI 伙伴重构 PRD 0.4

更新日期：2026-10-23。本文是产品与重构设计，不是功能完成记录。已按用户确认开始实施；稳定回退基线仍为 `0.3.0-s2`，Git 标签为 `v0.3.0-visual-baseline.1`。实施状态单独记录，不能把下列目标视为已交付。

本轮追加决定：先完成模型接口与离线伙伴任务，模型稍后选择。自然语言理解、模型对白、摘要与费用控制留待明确模型后接入；离线工作和原生生存不依赖模型服务。AI01、AI03、AI04 的在线部分仍是后续目标，本轮不以模拟回复冒充模型接入。

面向喜欢生存、探索、营地建设与角色陪伴的单人玩家，让玩家与少数长期 AI 伙伴共同生活：伙伴能理解任务、实际参与工作、应对危险，并记住有来源的共同经历。该目标人群与 AI 带来的体验增益仍需试玩验证，不能据此推导销量或市场成功。

采用 Necesse 作为唯一运行底座，保留其库存、制作、寻路、战斗、工作和保存能力；重构本项目的世界、场景、内容和伙伴接入层。GitHub 开源代码优先用于模型接入、记忆检索及任务控制。星露谷提供生活节奏、条件日程和个人事件的设计参考。现有像素清晰度、连续风动、夜景和投影是重构后的最低视觉标准。

## 1 已确认方向与本版范围

### 1.1 已确认的产品决定

| 决定 | 本版执行口径 |
| --- | --- |
| 核心体验 | 和 AI 村民一起生存、建设营地；伙伴的真实行动与长期经历同样重要 |
| 玩家规模 | 单人优先；少数有持续身份的核心伙伴，多人联机后移 |
| 世界模式 | 有限、种子生成、持久化的世界；可以按区域加载，不要求无限扩张 |
| 现有小岛 | 保留为视觉、交互与回归测试地图，不把其固定布局作为正式世界生成器 |
| 危险后果 | 核心伙伴默认重伤可救援、长期保留；永久死亡只作为后续困难规则候选 |
| 新内容 | 增加不同地形、动物、怪物及营地生活；扩展时优先增加素材和配置 |
| 技术策略 | 优先复用已有游戏机制和 GitHub 开源实现；明确移植与直接依赖的区别 |
| 画面标准 | 保持用户已接受的光影、风动、像素比例与道路表现；新地图也要达到这一标准 |

### 1.2 首版建议默认值

下列数量和具体内容是为实现排出顺序的设计默认值，尚不是用户逐项确认的规模承诺。调整这些内容时应优先改配置，不改变架构。

| 项目 | 首版建议 | 后续扩展 |
| --- | --- | --- |
| 核心伙伴 | 先验证小禾一个角色，再完成两名长期伙伴的协作；沿用小禾、林叔作为暂定角色 | 侦察、守卫、其他有个人经历的伙伴 |
| 世界形态 | 森林海岛、林地两种有限世界预设，共用同一生成框架 | 群岛、山地等预设；真正跨海航行另做机制 |
| 生态地形 | 森林、草地、岸边与水面；一处本作定义的洞穴区域作为跨区域验证 | 雪地、沙漠、沼泽、其他洞穴生态 |
| 动物与敌人 | 至少两种不同生活行为的动物、两种不同威胁行为的普通敌人 | 更多物种、精英与 Boss；具体造型和名称另做内容表 |
| 难度 | 标准生存、宽松生存；同一规则集调整资源、威胁和惩罚 | 困难生存、永久死亡、挑战规则 |
| 救援 | 现场救治、恢复伙伴关系和住所，并能护送返回；增加简单恢复状态 | 背负搬运、治疗床、完整伤病系统 |
| 时间 | 退出游戏停止模拟；明确暂停菜单暂停本地模拟，普通背包及任务面板不自动暂停 | 如以后支持离线生产，单独设计结算和上限 |

首版不包含完整四季、恋爱结婚、复杂疾病、积雪融化、船只航行、大型居民城镇和多人联机。接口需要容纳这些方向，但本期不预先实现其整套系统。

本 PRD 取代 0.3 PRD 中“只允许固定单岛、随机世界和 AI 后移”的阶段性范围。正式世界允许在本作注册的地表、洞穴及入口之间通行；仍然禁止意外跳回未适配的原版地图。0.3 已接受的视觉效果继续保留，夜间以最新调暗后的基线为准。

## 2 玩家完整体验

首版必须能完整走通以下流程：

1. 从 Mosslume 首页继续存档，或输入种子、选择世界形态和生存规则，创建新世界。
2. 在安全但资源有限的地点出生，找到建营地所需的食物、木材和石料。
3. 遇见伙伴，通过一个明确的小事件建立合作，分配住所及工作权限。
4. 通过任务按钮或自然语言安排采集、烹饪、搬运、跟随和建设协助，看到实际执行状态。
5. 建好住所、工作区、储物区和夜间光源；双方都需要食物、休息和安全条件。
6. 探索不同地形，遇到动物、敌人和资源点；通过装备、准备和协作获得更多建造能力。
7. 伙伴受伤时收到提示，找到并救治伙伴；伙伴保留身份、关系和已有经历。
8. 退出后重启，世界、营地、伙伴、任务与已发生的共同经历能一致恢复。

主循环为“探索与采集 → 分工与加工 → 营地改善 → 应对危险 → 获得新资源与共同经历”。个人事件应由实际生活触发，例如帮助伙伴脱险、完成一起建造的工作坊，不能仅靠无限生成对白推进。

## 5 功能来源与复用边界

### 5.1 保留原版机制，主要调整 UI 和内容

| 能力 | 可直接保留的代码能力 | 本作仍要做的工作 |
| --- | --- | --- |
| 物品、背包、箱子、掉落 | 原生库存、堆叠、物品交易与保存 | 物品定义、图标、分类、交互和共享权限表现 |
| 配方、工作台、烹饪与燃料 | 原生配方校验、材料扣除、加工执行 | 本作配方链、解锁、产出与耗时配置、UI |
| 种植和动物产物 | 生长、采收、饲养与产物基础 | 作物及动物的本作定义、平衡和完整素材 |
| 移动、寻路、碰撞、战斗 | 原生运动与战斗系统 | 角色比例、碰撞体与动画匹配，动作反馈 |
| 工作、搬运、储物占用 | 原生作业、预约、取消与存放 | 任务编排、玩家反馈和 AI 适配，不另造库存事务 |
| 新建世界及难度选项 | 原生表单和保存能力 | 恢复被首页隐藏的入口，去掉不受支持的选项 |
| 地图、迷雾、标记 | 原生发现和地图数据 | 本作地图外观、目标标记、伙伴位置权限 |
| 跟随、守卫、睡眠、避险 | 原生 HumanAI 和指令 | 用户入口、优先级与任务冲突处理 |
| 原生倒地及复活 | 默认 `canSettlersDie=false`、倒地状态和复活交互 | 本作救治材料、提示、恢复期及角色数据恢复 |
| 个性、生活质量和关系值 | 原生可保存的性格、需求和社交字段 | 精简为本作需要的状态，接入事件；长期经历另存 |
| 贸易与商店 | 原生交易、库存和货币处理 | 访客及货物配置、原创界面；首版后续内容 |

以上“可直接保留”表示机制继续运行，不能解释成所有相关页面都只需换图片。尤其工作、救援、世界生成要完成下面的适配。

### 5.2 在原版机制上改造

| 模块 | 需要改造的原因 | 实现方向 |
| --- | --- | --- |
| 有限世界 | 原生当前生成框架与本项目固定岛都不等于目标世界规则 | 在原生区域框架上增加有限边界、生态分布、连通性及资源保障 |
| 生成与测试初始化 | 当前资源箱、燃料和居民是测试配置 | 分离测试场景、出生包、伙伴加入事件、正式资源经济 |
| 多建筑和视觉位置 | 显示、门、窗灯与房屋位置存在多处硬编码 | 同一个结构实例提供脚点、碰撞、屋顶、灯、床和交互点 |
| 光影扩展 | 全图遍历和整图接收贴图不能直接放大到大世界 | 按已加载区域注册光源/遮挡，按可见范围更新；跨区共用世界坐标 |
| AI 任务控制 | 模型输出不能直接改变物品或世界 | 验证意图，再提交原生任务，按实际事件更新结果 |
| 救援 | 原生倒地会取消工作、掉落工作物品并暂时移出聚落 | 恢复稳定伙伴身份、住所和权限，按实际掉落处理物品，不复制 |
| 伙伴生活 | 原生聚落员工机制需要形成少量伙伴的生活体验 | 加角色日程、共同事件、偏好和关系反馈，保留本地生存行为 |
| 存档 | 原生不知道新增的 AI 请求、任务意图和记忆 | 扩展版本化保存；读档先核对世界实体再恢复可执行任务 |

### 5.3 星露谷的采用方式

本地星露谷参考是 C#／.NET／MonoGame 体系，当前运行底座为 Java／Necesse；其人物、时钟、库存和保存类型不兼容。没有一套完整星露谷功能可以直接粘入当前项目后仅改 UI [E08]。

采用条件日程、生活节奏、事件触发及个人关系反馈的设计；如确有必要，移植独立规则并接到 Necesse 的同一时钟、实体和保存系统。工作地点使用伙伴实际的家、农田、厨房和营地，不照搬固定地图坐标。已有原生关系、作物、动物能力先复用，避免并存两套等价系统。原作人物、故事和对白不作为本作默认内容。

### 5.4 GitHub 开源组件的实际接入路线

截至 2026-10-23，已开始实施：FastNoiseLite Java 源码用于种子地形；AI Town 的相关性、重要性、时效归一化排序移植到 Java，绑定真实游戏事件。固定提交、采用文件与 MIT 许可证保存在 `third-party/` 及包内许可证中。其余项目仍为候选，特别是 LangChain4j 随模型选择后移；没有完整安装 AI Town 或 Mindcraft。

| 项目 | 本版定位 | 采用方式 | 不能直接提供的部分 |
| --- | --- | --- | --- |
| [LangChain4j](https://github.com/langchain4j/langchain4j)，Apache-2.0 | Java 模型接入首选 | 引入最小所需模块，使用模型适配、结构化输出和工具声明 | 没有现成的本作 NPC、采集执行器或完整长期记忆 |
| [AI Town](https://github.com/a16z-infra/ai-town)，MIT | 记忆检索与交流模块首选移植来源 | 移植摘要、相关性/时效/重要性检索及带来源的反思逻辑 | TypeScript、Convex 和浏览器世界需换成游戏事件及本作存储 |
| [Mindcraft](https://github.com/mindcraft-bots/mindcraft)，MIT | 动作生命周期与执行反馈移植来源 | 选取取消、打断、超时、失败结果和循环停止逻辑，接原生作业 | Mineflayer 和 Minecraft 动作不能用于 Necesse；不接入动态生成执行代码能力 |
| [Generative Agents](https://github.com/joonspk-research/generative_agents)，Apache-2.0 | 记忆、计划与反思的补充研究 | AI Town 模块不足时按需借鉴独立逻辑 | 不默认运行 Python／Django 模拟器，不引入第二套世界 |
| [FastNoiseLite](https://github.com/Auburn/FastNoiseLite)，MIT | 可选地形算法补充 | 原生生成表现不足时使用 Java 噪声和域扭曲 | 不负责世界连通性、出生保障、营地模板或持久化 |

实际运行路线为一个 Java 模型接入层、一套本作事件/记忆数据、一套连接原生作业的任务适配器。AI Town 和 Mindcraft 是选取代码的来源，不能在未做移植时写成已完整集成的插件。遇到适配障碍，先缩小依赖或采用其他兼容的现成组件，不直接改为自研整套模型框架。

包内 JRE 为 Temurin 17.0.19 x86_64，编译脚本目标为 `--release 17`；LangChain4j 基础模块的 Java 17 要求相符，但依赖、类加载、打包和网络仍需验证。本次研究到的主分支为 SNAPSHOT，生产依赖必须另选并锁定正式发布版本 [E09]。

## 6 世界 地形与地图模式

### 6.1 三层独立配置

| 层级 | 定义 | 示例 |
| --- | --- | --- |
| 世界形态 `WorldPreset` | 有限边界、区域布局、陆水比例、出生策略、区域层级和模板配额 | 森林海岛、林地；未来群岛 |
| 生态地形 `BiomeDefinition` | 地表、植物、资源、动物、敌人、光色、声音及相邻过渡 | 森林、草地、岸边；未来雪地、沼泽 |
| 生存规则 `RuleSet` | 资源消耗、敌人威胁、死亡后果、时间与再生规则 | 标准、宽松；未来困难 |

世界尺寸、种子和上述选择在创建前展示。世界形态不能偷偷改变难度；外观为雪地也不自动意味着已经实现冻伤。不同规则使用相同格式，所需参数集中维护。

### 6.2 生成约束

- 保存种子、生成器版本、内容包版本、世界形态和规则快照。同版本和同种子应得到相同基础布局；玩家后续行为不要求可预测。
- 区域随机数由世界种子、区域坐标、生成阶段及版本独立确定，不能依赖玩家探索先后或一个共享随机数流的消耗顺序。
- 生成先确定有限边界、区域及关键位置，再布置地形、路径、资源、动植物和场景模板。允许区域按需生成，有限世界并不要求一次加载全部内容。
- 校验安全出生点、第一天基本资源、伙伴加入地点和阶段目标可达。第一次伙伴可能倒地前，基本救治方式必须已可解锁，材料有可达来源。无法满足时在有次数上限的范围内重选候选布局；最终失败要给出可理解提示，不能进入无路可走的世界。
- 地形接缝、岸边、洞穴入口和返程使用统一坐标与注册关系。所有越界、传送、复活和读档位置校验共用目标白名单。
- 道路沿实际地形和可达节点生成，使用现有自然边缘表现；不能把大片规则矩形作为主要道路。
- 房屋、遗迹、资源点和营地使用可嵌入的模板，模板同时声明占地、出入口、物件和空间要求，防止生成在水中或堵死路径。

### 6.3 旧世界与新增地图

默认保留已生成区域，加载存档优先于重新生成。现有世界继续使用创建时锁定的生成器与内容规则；新增地形默认在新世界中生效，不能因软件更新而让旧世界未探索区自动混用另一套算法。

为以后扩展旧世界预留 `WorldExpansionPlan`：记录新增区域、边界衔接、内容版本和回滚信息。此接口本期仅定义兼容边界，不交付玩家可用的扩张工具。迁移不得清空旧营地、移动箱子或重置伙伴。

旧固定测试岛仍用原资料运行，作为回归档保留。0.4 默认使用新测试资料目录和新正式世界，旧岛不自动转换成随机世界。

## 7 生存 营地与生态

正式生存从有限出生物资开始。玩家与伙伴通过采集、种植、加工和探索补给食物及燃料，营地提供储物、制作、休息与防御收益。篝火的真实燃料与照明状态一致，不能延续测试地图长期赠送燃料的配置。

| 系统 | 首版要求 |
| --- | --- |
| 生存资源 | 有可理解的生产与消耗，基础资源能再生或有可达替代来源；避免初次失误造成无法恢复的必败局 |
| 玩家失败 | 建议默认在营地或安全点恢复，并有可找回的损失；具体损失数值随生存规则配置，避免单次失败清空整个世界 |
| 营地建造 | 玩家能放置多个住所、床、箱子、工作台、烹饪设施、围栏及光源；占地、材料、入口和居住条件需要校验 |
| 建造协作 | 伙伴能为已确认的建造任务准备和搬运材料；原生能力不足的施工动作通过独立适配器实现，模型不能随口生成建筑 |
| 共享库存 | 箱子和工作区可分配取用权限，保留种子、口粮或指定材料；伙伴不能无视保留量消耗全部库存 |
| 动物 | 有栖息地、活动时段和至少一种生活行为，如采食、逃跑、可饲养生产；不能仅为不会行动的装饰 |
| 敌人 | 行为、攻击提示和掉落可区分；夜间威胁与地形相关，生成不会直接落在玩家或床位上 |
| 生态上限 | 出生密度、再生周期、区域承载和玩家建设安全范围可配置；不能无限累积实体 |
| 进度 | 建成营地、保障供给、共同探索三段目标；由真实建筑、储备和事件解锁，不由聊天内容直接授予奖励 |

原生能提供的耕种、动物产出、敌人行为和配方继续保留。星露谷的日程与生活反馈用于改善节奏，不作为另一套生存数值系统。

## 8 AI 伙伴的功能和执行约束

### 8.1 伙伴形象与日常

每名伙伴具有稳定的 `companionId`、显示名称、个性、擅长工作、偏好、住所、需求和关系状态。日程随实际住所、设施、天气或危险调整。吃饭、休息、逃生、战斗和已接受的简单工作由本地规则执行，模型回复不决定是否及时避险。

伙伴可以理解任务、解释困难、讨论近期经历，依据已知食物和燃料状况主动提醒。原生个性与生活状态提供稳定事实，语言模型负责表达和高层规划。首版不要求所有路人、动物和怪物调用大模型。

### 8.2 玩家指令到真实工作

```text
玩家文字或任务按钮
    → IntentRequest（任务意图、对象、数量、范围）
    → 规则校验与必要澄清
    → TaskRecord（可见任务、权限、前置条件、状态）
    → NativeJobAdapter（原生寻路、作业、库存预约）
    → 实际事件与结果
    → 任务 UI、伙伴反馈、可追溯的记忆
```

以“收集 20 个木材放进这个箱子”为验收例子：确定玩家指向的箱子和授权采集范围，检查工具与资源，执行采集和存放，依据真实物品入箱数量结算。若范围内没有资源、道路被堵或箱子满，伙伴明确报告原因，提供可执行建议。不能先说完成，再在后台补结果。

首批动作包括移动、跟随、守卫、采集、采收、搬运、存放、加工、补充燃料、建造备料和现场救治。每个动作都要声明前置条件、输入、可打断点、成功事件和失败原因；对应能力没有实现时不向模型开放。

自然语言与按钮共用同一任务入口。玩家可看见执行者、目标、进度、当前阻碍，以及暂停、继续、取消入口。模型认为目标不明确时，游戏内询问目标位置或数量；不会把任意缺失值填成高风险行动。

### 8.3 状态 并发与打断

任务状态统一为 `proposed → validating → queued → running → succeeded`，并支持 `blocked`、`paused`、`failed`、`cancelled`。每次状态变化有原因及世界时间。

- 危险、倒地和玩家取消可以打断任务；让出原生资源预约，保留实际已完成数量。恢复前重新检查目标、材料和权限。
- 两名伙伴与玩家同时取用物品时，以原生库存与预约结果为准。不维护一份模型自行推测的可消费库存。
- 模型请求由游戏侧绑定 `worldId`、`companionId`、`requestId`、任务/状态版本和存档会话标识，不信任模型自行声明的身份。取消、暂停、读档、切换世界或退出后失效的回包不执行，也不更新任务、关系、长期记忆或触发后续请求；过期摘要同样被丢弃。
- 每名伙伴的同一记忆会话串行处理；网络、检索、摘要在后台运行，写世界的动作交回原生游戏线程。
- 不可执行的动作、未注册物品、越界坐标和过期目标被拒绝。重试次数和工具调用轮数受限，不能永久原地循环或持续计费。

### 8.4 记忆与知情范围

| 数据 | 保存内容与约束 |
| --- | --- |
| 发生的事件 | 谁、何时、何地、做了什么、实际结果，引用唯一事件 ID |
| 伙伴知道的事情 | 亲眼经历、玩家告知或他人转述；标明来源与是否确认，不自动知道全地图 |
| 个人看法 | 个性和已知经历形成的判断，允许主观，但不能改写客观库存、伤势或任务结果 |
| 对话上下文 | 有长度上限的近期聊天，压缩后保留关键事件来源 |
| 长期经历 | 根据重要性保留的共同建造、救援、承诺等，能在后续交谈中检索 |

长期记忆采用 AI Town 等项目的检索与摘要机制，经移植后绑定游戏事件。首版可以先按事件类型、人物和时间检索，再视效果加入向量检索；向量索引必须可重建，不能成为唯一保存事实的地方。存档删除或角色记忆重置需要同时处理相应索引。

关系变化由可检查的游戏事件与规则触发，模型可以表达其意义，不能自行把关系值改满。关于未经历、未获知的事件，伙伴允许回答“不知道”。模型生成的计划只能记为计划，执行成功后才能形成完成事件。

### 8.5 救援与伙伴连续性

复用原生倒地与复活，不重建生命状态机。新增可见救援标记、现场救治交互、基础恢复状态及回营指令；默认规则不因模型失联造成伙伴永久丢失。

原生倒地会取消工作、掉落工作物品并暂时移出聚落。伙伴身份与记忆必须独立于暂时的聚落成员关系；恢复时核对住所、工作权限和物品所在位置。不能把招募保留时间误当成死亡倒计时。背负搬运、治疗床与复杂伤病作为后续规则模块，不假定原生已提供 [E06]。

### 8.6 模型失败 预算与玩家控制

设置中显示模型服务状态、启用/停用、连接配置和调用预算。具体供应商、云端或本地部署及费用上限尚待选型；本版以可替换提供商接口实现，不能把未测价格写成每小时成本保证。

模型超时、断网、输出不合法或达到限额时，显示简短原因，保留原生工作和生存行为，玩家仍能通过按钮分配任务。关键请求可重试，重复失败进入降级状态。日常行为不逐帧调用模型，只有新任务、重要事件或明确交谈触发调用。

记录请求延迟、输入输出 token、工具轮次、超时、失败和缓存命中；费用按实际供应商账单口径汇总。凭据不写入仓库和普通日志；发给模型的是伙伴需要的场景摘要及相关记忆，不是整份存档或用户电脑文件。

## 9 重构结构与扩展接口

以下是接口职责和数据契约，不承诺实现时必须使用同名 Java 类。以一个可运行闭环验证后再推广，避免先创建大量空接口。

| 模块或接口 | 本版职责与必要数据 | 允许的后续扩展 |
| --- | --- | --- |
| `WorldDefinition` | 世界 ID、种子、有限边界、预设、规则、生成器及内容版本 | 新地图形态、尺寸、生成策略 |
| `BiomeDefinition` | 地面、邻接过渡、碰撞/通行、资源与物种表、环境声光 | 在已有机制下添加新地形 |
| `SceneTemplate` | 可嵌入区域、占地、入口、对象、资源约束和放置条件 | 村庄、遗迹、洞穴房间、资源点 |
| `StructureDefinition / StructureInstance` | 稳定 ID、位置、朝向、脚点、占地、门、屋顶、灯、床位和工作点 | 新房屋与工作设施；灯和碰撞随实例移动 |
| `ResourceDefinition` | 采集标签、工具条件、生长/再生、掉落、状态素材 | 新树、矿、作物，无须逐种改写 AI |
| `SpeciesDefinition / CompanionDefinition` | 行为预设、能力、栖息地、动画、碰撞、属性、日程和关系参数 | 新动物、敌人、伙伴；新行为通过注册扩展 |
| `InteractionRegistry / ActionAdapter` | 动作 ID、输入、前置条件、权限、原生执行映射、取消和结果 | 新工作站或特殊动作；只有注册能力可被 AI 使用 |
| `TaskService` | 任务状态、执行者、目标、进度、优先级、版本和原生预约关联 | 复合任务、多人任务的未来扩展点 |
| `CompanionKnowledge / MemoryStore` | 事件 ID、来源、知情范围、摘要、检索和清理 | 新模型或检索方式，不改伙伴事实存储 |
| `ModelProvider` | 结构化输入输出、超时、取消、限额、使用量 | 更换云端提供商或本地模型 |
| `WorldEventBus / RuleModule` | 真实事件发布和确定性规则处理，定义前后置顺序 | 季节、温度、伤病等新机制；需要代码实现 |
| `VisualComponent / RegionSceneQuery` | 像素规格、层级、风动权重、发光、投影轮廓和局部查询 | 新素材共用既有渲染；未来天气及受光配置 |
| `SaveExtension / MigrationRegistry` | 命名空间、schema 版本、原生实体映射、一致保存标记与迁移 | 新系统数据、旧档兼容与扩展区域计划 |

配置采用可审查的数据文件并提供 schema 校验；格式在第一个内容模块中统一。引用使用稳定字符串 ID，避免把显示名称、素材顺序或运行时临时对象号当成持久身份。内容包登记 `packId`、版本、依赖、素材来源和兼容范围。

启动时验证内容包，并在原生注册表关闭前，通过通用工厂实例化支持的地块、物件、物种与行为。普通新内容不需要逐项手写 Java 注册类；安装或更新内容包后重新启动游戏，本版不要求运行中热加载。旧存档引用的内容 ID 不得被重新分配给其他对象。

数据配置的范围应有限且明确：既有行为的参数和组合可以配置，新物理、新输入、新状态机或新网络协议需要实现。不要为所有未知玩法预设无限通用脚本系统。

### 9.1 添加内容时具体要做什么

| 新增内容 | 素材与配置 | 何时需要写功能代码 |
| --- | --- | --- |
| 另一种树 | 树冠、树干、状态、脚点、风动权重、投影、采集标签和掉落 | 产生现有系统没有的交互，例如可攀爬 |
| 新的雪地外观 | 地表与过渡、植物、物种、环境光声、生成权重 | 冻伤、积雪、融雪等真实规则 |
| 新动物 | 方向动画、碰撞、行为预设、栖息地、产物、生成限制 | 现有行为库没有的驯养、骑乘或复杂协作 |
| 新工作台 | 图像、占地、交互点、配方和任务能力 | 新加工流程无法用既有生产任务表达 |
| 新地图预设 | 边界、生态权重、模板、出生和资源约束 | 航行、载具或全新层级连接方式 |
| 新伙伴 | 角色素材、人格、职业、偏好、日程和个人事件 | 确有新工作能力时增加动作适配器 |

最低扩展验收为添加第二种地形、新树和一个新可交互对象，仅增加内容定义及素材即可生成、碰撞、投影、保存和被既有 NPC 工作识别。若必须在世界主循环或渲染器里新增一串按对象名判断的分支，说明本次扩展目标尚未完成。

## 10 保存 加载与时间一致性

沿用原生世界、区域、实体与物品保存。新增任务、记忆和内容版本挂接同一存档边界，不引入另一套可独立改变世界事实的数据库。

- `companionId` 映射原生实体；倒地、离开聚落、跨区和读档不改变长期身份。
- 任务结果用唯一任务/动作标识去重，库存变化与结果事件关联。崩溃重启不得重复扣材料、发物品或写成功经历。
- 保存时记录一致性检查点。若附加数据无法与原生保存原子提交，必须记录检查点和恢复状态，先核对原生事实再恢复任务，不能盲目重放动作。
- 加载顺序为读取存档元信息 → 核对内容版本及原生注册是否齐全 → 加载世界和实体 → 恢复身份与关系 → 校验任务目标和运行引用 → 恢复记忆与可重建索引。缺少注册项时先解决内容兼容或以匹配配置重启，不能先反序列化再补救。旧网络请求不会因读档而重新生效。
- 首版建议让玩家附近、同行伙伴及一个主营地保持有上限的原生区域模拟，使玩家探索时营地仍可工作；区域范围和数量在 M2 验证后固定。超出模拟范围的任务暂停并显示原因，返回后重新校验；本版不增加离屏摘要生产系统，不凭空结算未模拟的战斗、救援或材料。不得为了 AI 长期加载全地图。
- 暂停、退出和读档中断网络请求的执行资格；跨区域、暂停和恢复时间采用同一原生时钟。
- 找不到内容版本或 ID 时给出可定位错误并保留备份，不开始写回该存档，禁止静默替换为错误对象或自动删除世界。

## 11 画面 美术与性能

现有清晰像素显示、连续树冠风动、自然小径、暖色局部灯光、树与物品投影、岸边向海面投影继续作为基线。保留已采用的 Sharp Shimmerless、Simple Wind 和 SDV-Radiance 相关移植代码及来源记录，重点改造其场景数据依赖，不再更换整套画面方案。

| 内容 | 接入规范 |
| --- | --- |
| 人物与伙伴 | 原生像素尺寸、统一角色比例、脚点与碰撞；站立、行走、工作、攻击、受伤、倒地按实际动作覆盖 |

素材按“源图 → 运行导出 → 已绑定 → 可见状态完整 → 运行验收”登记，生成图片不等于已接入。先审查既有素材包，优先补缺失动作和状态，避免再堆一批没有绑定的图。

当前基线仍未达到参考视频的完全一致，海水表现等差异保留在视觉待办中；本版扩展不能以玩法变多为理由降低已有质量。性能方面，网络调用不得阻塞渲染，光源与遮挡按区域增量更新，不再按世界总面积遍历。

验收固定机器、窗口、帧缓冲、时间与光源条件，同时检查原尺寸截图、连续录像和帧时间。基线记录为逻辑窗口 1200×900、帧缓冲 2400×1800、上限 60 fps；6 秒数据不足以冻结长期性能指标 [E02]。第一阶段重新建立同机重复测量，记录 p95/p99、长帧、内存和区域数量，冻结允许波动范围；后续阶段按该范围验收。目标为常用 60Hz 显示下稳定呈现，不能只以平均 FPS 宣称通过。
